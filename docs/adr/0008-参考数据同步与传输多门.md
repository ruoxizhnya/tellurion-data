# ADR-0008 · 参考数据同步与传输多门（QT-40 三缺口处置）

- 状态：已采纳（2026-11-10）
- 决策：本仓（数据面负责人）
- 关联：QT-40（X1）、SVC-DATA-G3、ADR-0003（传输自持）、ADR-0007（本仓自持传输与调度）、`docs/db-schema.md` §9

## 背景

QT-40 在 X1d 关闭后只剩三块：`ingest.raw` 归档面未搬、传输只有 Tushare 一门、7 张零写者表。前两轮（G3、X1c）把「写面归属」与「传输/调度」落了，但零写者与归档面一直挂在台账上。本笔的目标不是「把所有空接口都填上」，而是**给每一块一个可核查的归属**：值得做的补上，不值得做的按挂起落账（带重开条件）。

## 决策一：`ingest.raw` 归档面不搬（⏸ 挂起）

**事实**：core 的 raw 归档随 `pkg/data` 在 `a96d836`（2026-11-08）整体删除；本仓 `internal/ingest` 的传输窄口返回**解析后的结构体**，没有 raw 字节通道；`ingest.raw` 今天零写者、零读者、无保留期。

**选项与代价**：

- A · 在传输层加 raw sink，逐请求落原始响应：需改窄口（所有传输实现都要接）、定保留期/脱敏/容量上限、并至少有一个回放消费者。
- B · 用归一后的点位回放（`ingest.data_points` / `market.*`）代替 raw 归档。

**结论**：选 **B + 挂起**。归一后的数据已能重放；raw 只在「怀疑归一化本身错了」时才有额外价值，而当前没有这种取证需求。**重开条件**（三条同时满足才另立单）：① 出现明确的回放/审计消费者；② 单内给出保留期、脱敏与容量上限；③ 选定挂载点（传输层 sink 或独立归档进程）。在重开前，生产取数**不留 raw**——这与现状一致，只是从「未落项」变成「有意的终态」。

## 决策二：传输多门 —— 东财与 Alpha Vantage 接线，Mootdx 挂起

**事实**（2026-11-10 `cmd/dataservice/main.go` 实测）：

| 门 | 代码在仓内 | 装配条件（处置前） | 处置 |
|---|---|---|---|
| Tushare | ✅ | `TUSHARE_TOKEN` 有值 | 不变 |
| Eastmoney | ✅（HTTP 客户端） | **未接线** | **接线**：`ingest.NewEastmoneyClient()` 无凭证，恒装配 |
| Alpha Vantage | ✅ | **未接线** | **接线**：`ALPHA_VANTAGE_KEY` 有值才启用 |
| Juchao / Xueqiu / Yahoo | ✅（自带默认端点） | connector 恒启用 | 不变 |
| Mootdx | ❌ 仅接口（`Transports.Mootdx`） | 无实现 | **⏸ 挂起** |

**结论**：东财与 Alpha Vantage 是「代码已在、只差一行装配」，补上即可让 `capital_flow` / `sectors` / `top_list` 之外多一条独立于 Tushare 的腿，避免单点。**Mootdx 不做**：需要 TDX TCP 二进制协议实现或引第三方 SDK，还要柜台网络/账号；当前无分钟线/实时行情消费者。**重开条件**：出现分钟线或实时行情消费方 + 选定 SDK 并验证网络可达。

## 参考数据为什么旁路 ETL（关键设计取舍）

`stocks` / `trading_calendar` 是 C 集参照表：没有 `visible_at` 列、没有 data_type 声明。点位管线（`FetchRequestFromParams → Pipeline → BulkInsert`）的两条核心语义对它们**不成立**：

1. **PIT 整批门**：`BulkInsert` 要求整批 `visible_at` 非空，否则整批拒收。参照表没有「可见时间」这个概念。
2. **幂等内容比对**：点位写面同内容 no-op、异内容整批回滚（历史值不可改）。参照数据的语义相反——名称、行业、状态会变，**后到者覆盖可变列**才是对的。

因此新开一条窄腿：

```
TushareTransport.trade_cal / stock_basic
  → ingest.ReferenceTransport（窄口，只增不改点位接口）
  → syncjob.ReferenceRunner（job_type = stocks / trading_calendar，保留字面值）
  → store.ReferenceWriter（ON CONFLICT upsert）
```

`job_type` 因此有两个**保留**取值；`Runner.Execute` 在最前面分流，参考数据作业不会掉进点位管线被当成「未声明 data_type」。这条例外写进 `internal/sync/job.go` 的包注释与 `docs/api-schema.md` §4。

**为什么不是新增两个 data_type**：data_type 是契约（contracts `dataprotocol`）的单源，新增会牵动契约发版、声明表、归一化器与闸门分类；而这两张表根本不走点位存储。用保留 job_type 是更小的接口面。

## 代价与已知限制

- `market.trading_calendar` 的主键只有 `trade_date`：经查无多交易所消费者，按**单一 A 股交易日历**写死（写侧混批拒写 + DDL CHECK + 文档声明），不改主键。证据与重开条件见 ADR-0009 决策一。
- `stocks.delist_date` 已落库（2026-11-11，ADR-0009 决策二）：DDL 补列 + 幂等 `ALTER ... ADD COLUMN IF NOT EXISTS` + upsert `COALESCE`，读面改直读列名；历史票池可按退市日截断，不再只靠 `status`。
- 参考数据作业只在本跳接线；无 `TUSHARE_TOKEN` 时以 `misconfigured` 响亮失败，不会静默成功写 0 行。
- 真实源响应已核（2026-11-11，`TUSHARE_TOKEN` 可用）：`stock_basic` 的 L / D 查询均返回请求的 9 列（L 5580 行、D 343 行；`delist_date` 无值时是空串），`trade_cal` 返回 4 列（10 行；`is_open` 是 JSON 数字 1/0）。解析契约由 `internal/sync/reference_contract_test.go` + `internal/sync/testdata/*.json` 钉住：缺列/改名 ⇒ `ErrTransportDataQuality`，作业在开事务前失败；多余列（`area` / `market` / `is_hs`）显式忽略。线上形状不再挂起；生产部署后的作业级核对仍属上线验收（见 `docs/TASKS.md` QT-40）。
