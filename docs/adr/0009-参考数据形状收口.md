# ADR-0009 参考数据形状收口：交易日历单交易所、退市日落库

- 状态：已采纳（2026-11-11）
- 关联：QT-40、ADR-0008、`docs/db-schema.md` §9.1、`docs/dataflow.md` §2「参考数据」
- 范围：`market.trading_calendar`、`market.stocks` 的存储形状；不改 DTO、不改点位管线

## 背景

ADR-0008 把参考数据（`stocks` / `trading_calendar`）接进了本仓写面，但留了两条已知限制：日历主键只有 `trade_date`（多交易所会覆盖 `exchange`），`stocks` 不落 `delist_date`（退市只能靠 `status` 表达）。本 ADR 判断这两条是否真实风险，并给出收口方式。

## 决策一：`trading_calendar` 按「单一 A 股交易日历」写死，不改主键

### 事实与证据

- 唯一读方 `store.TradingDays` 的 SQL 只选 `trade_date`，不筛也不返回 `exchange`；`GET /api/v1/trading/calendar` 的响应是 `[]time.Time`，没有交易所维度。
- `ReferenceRunner` 的日历作业默认 `exchange=SSE`；2026-11-11 线上核对 `trade_cal` 返回的 `exchange` 恒等于请求值。
- A 股各交易所（SSE / SZSE / BSE）的交易日一致：同一批法定休市，没有「上交所开市、深交所休市」的日期。

### 选项与代价

- **A · 改复合主键 `(exchange, trade_date)`**：要改 DDL、迁移既有行、改读方（去重或按交易所筛选）、改接口响应形状与 `calendar_hash` 输入，代价落在多个仓；服务的是一个**不存在**的消费场景。
- **B · 保持主键，写死单交易所假设**：写侧拒混批 + DDL `CHECK`（新库）+ 文档声明；读方与契约零改动。

### 决定

选 **B**。`trading_calendar` 是「一张 A 股日历」，`exchange` 列只是**最近一次写入来源**（provenance），不是维度。

落地：

- `store.ReferenceWriter.UpsertTradingDays` 在开事务前检查批次；混入多个交易所返回 `ErrMixedTradingExchanges`，一条 SQL 都不发（跨作业先后写不同交易所仍允许，因为值相同）。
- DDL 把 `exchange` 收紧为 `NOT NULL DEFAULT 'SSE'` + `CHECK (exchange IN ('SSE','SZSE','BSE'))`。新建库建表即带这两条；**既有库**（建于收紧之前）由启动期的受保护回填补齐，见下节。
- `docs/db-schema.md` §9.1 明示「单交易日历；`exchange` 仅 provenance」。

### 既有库回填路径（2026-11-12 追加）

**为什么不改语义**：回填只是把「新建库建表时就有的约束」补到建于该约束之前的库上——不改列、不改数据、不改读写契约。同一条输入在回填前由写侧 `ErrMixedTradingExchanges` 拦截，回填后由约束兜底，判据与拒绝面完全一致（都只允许 `SSE` / `SZSE` / `BSE`）。因此它不推翻决策一，而是把决策一在既有库上的落地补完。

**实现**（`internal/schema/guard.go` + `cmd/dataservice` 的 `applySchema`）：启动时在全部建表语句之后调用 `ApplyGuardedConstraints`：

1. `pg_constraint` 已有该约束 ⇒ 跳过（幂等）；
2. `pg_attribute.attnotnull` 已为真 ⇒ 不重复收紧；
3. 否则先 `SELECT` 校验目标列无 NULL、无越界值，通过才 `ALTER COLUMN ... SET NOT NULL` + `ADD CONSTRAINT`；
4. 校验不通过 ⇒ **不加约束、只打 WARN**（违规行数 + 样例），服务照常启动——历史脏库不许把启动打死。

三处必须同步：`internal/schema/market.go` 的 `CREATE TABLE` 定义 → 启动期回填（`GuardedConstraints()`，由 `applySchema` 调用）→ `docs/db-schema.md` §9.8 核对表。新增「建表定义里有、既有库可能缺」的约束时，两处代码各加一条 `GuardedConstraint`，并补 PG 用例（干净表补上 / 脏表跳过并告警）。

### 后果

- 误用「按交易所分片并发写」会在作业层响亮失败，而不是静默互相覆盖。
- 读方不需要去重，接口形状不变。
- 将来真要分交易所日历时，读方必须先能表达交易所维度。

### 重开条件

出现按交易所区分的消费者（响应形状或 `calendar_hash` 需要 `exchange` 维度）时，另立单：改主键为 `(exchange, trade_date)`、迁移既有行、改读方与契约响应，并补跨交易所差异的线上证据。

## 决策二：`stocks.delist_date` 落库

### 事实与证据

- `market.Stock` 已有 `DelistDate` 字段，Tushare 解析也已产出（2026-11-11 线上核对：`list_status=D` 的 343 行都带退市日），但 DDL 与 `ReferenceWriter` 都把它丢弃，读面只能用 `to_jsonb(t)->>'delist_date'` 探针兼容旧库。
- 回测的历史票池若只按 `status='delisted'` 过滤，无法回答「某个交易日这只票是否已退市」：退市日前纳入是前视，退市日后才纳入是幸存者偏差。历史退市日期是 survivorship-bias 治理的必需输入。

### 决定

补列并贯通写读：

- `market.stocks` 增 `delist_date DATE`（可空）；追加幂等语句 `ALTER TABLE IF EXISTS market.stocks ADD COLUMN IF NOT EXISTS delist_date DATE`，让既有库前滚。
- `UpsertStocks` 写入 `delist_date`，冲突时 `COALESCE(EXCLUDED.delist_date, s.delist_date)`：源端没给不擦已有值。
- 读面 `Stocks` / `Stock` 改直接列名，删除 jsonb 探针。`public.stocks`（core 旧库）本就有该列，两种 schema 都成立。

### 后果

- 历史票池可以按 `delist_date` 截断；`status` 仍是「当前是否退市」的快照，两者不互相替代。
- 列可空：在市股票为 NULL，语义是「未退市」，不是「未知」。
- 没有通用迁移框架，前滚依赖 schema 执行时的幂等 `ALTER`；老 DDL 的 `CREATE TABLE IF NOT EXISTS` 不会补列，所以 ALTER 必须单列一条。

### 重开条件

无。若将来需要退市类型/原因，另立列，不塞进 `delist_date`。
