# 0005 · 鉴权接入：kit net/http 适配 + REV-17 移植

- **状态**：已裁决（来源：裁-15，2026-10-25）
- **场景**：旧 `core:cmd/data` 已有完整 REV-17 策略表（排程管理 admin / 其余变更 trader / `POST /screen` 与 `POST /api/v1/ohlcv/bulk` any-authenticated），而新 `cmd/dataservice` **零鉴权实现**；`config/data-service.yaml` 已声明与 analysis 共用的 `AUTH_JWT_SECRET`，配置在说谎。kit `v0.1.1` 已提供 `auth/httpadapter`。
- **决策**：
  1. **机制在 kit、策略在本仓**：`internal/httpapi/auth.go` 实现 `Authorizer`，内部走 `httpadapter.Authenticate` / `Authorize`；`internal/httpapi/policy.go` 是唯一策略表。
  2. **实际路由**（`servedPolicy`）：`GET /health` = Public；`GET /datasets/resolve`、`GET /datasets/{hash}` = viewer 及以上。**（2026-10-25 裁-17 追加，不改本条其余口径）** 这两条的 Roles 再加 `service`——调用方是 core / analytics 的服务账号长期 token，不是人类会话的 `trader`；`/health` 仍 Public 不按角色起。服务 token 在 kit 侧就是 `kind=access` 上的一个角色串（`IssueServiceToken` 铸 `KindAccess`），所以本仓**不因它升 kit 版本**，pin 的 `v0.1.1` 已能验。守卫 `TestServedPolicyServiceRole`。全部路由由同一份 `routes()` 注册并逐个包 `requireAuth`。
  3. **REV-17 逐条移植**（`legacyREV17`）：旧服务 28 条策略原样搬入本仓（条目与档位一一对应）。这些端点尚未迁入，本仓不注册它们；表作为迁移期参照，端点进来时直接挂闸，不再重新拍一次角色。
  4. **启动闸**：`/health` 公开但仍过闸（未装配 Authorizer → 503，服务端装配错误应显式暴露）；有 secret 开鉴权；无 secret + 回环 = 开放；**无 secret + 非回环 = 拒绝启动**（默认 `:8081` 全网卡，必须显式配置 secret 或声明 `AUTH_INSECURE_EXPOSURE=loopback-published`）。
- **理由**：token 校验与角色 any-of 是跨服务同一套语义，留在 kit 才不会漂移；策略是数据面业务，留在本仓才可审计。路由表与策略表同源注册 + 双向守卫，漏登即红。
- **代价 / 后果**：
  - 新增对 `github.com/ruoxizhnya/tellurion-kit v0.1.1` 的依赖（编译闭包含 gin，源码不 import gin）。
  - **默认启动行为变了**：裸 `go run ./cmd/dataservice`（`:8081` + 无 secret）现在会被启动闸拒绝；本地开发需 `-addr 127.0.0.1:8081` 或显式 `AUTH_INSECURE_EXPOSURE=loopback-published`。
  - 旧端点迁入前，REV-17 表只是参照，不产生运行时保护；真保护仍在 core `cmd/data` 的 gin 中间件。
  - core `proxyRequest` 必须透传入站 `Authorization`，否则 `POST /api/v1/ohlcv/bulk` 在网关处被数据服务 401；该腿已于 2026-10-25 落在 core。
  - **`service` 角色的配发不在本仓**：本仓只保证「给了 `service` token 就能读这两条」；给 `data-service` 配 `JWT_SECRET` 与调用方 token 属 core QT-71 腿，那半边没落之前生产上仍然读不到——接受面加宽不等于配发已完成。
- **替代关系**：不替代 0001–0004。旧 `cmd/data` 的 REV-17 表仍是其运行时真相；本表只是迁移目标。

## 追加（2026-10-25，kit `KT-11` / `v0.1.4`）· 决策 2 里「不因服务 token 升 kit」那句作废

原文「服务 token 在 kit 侧就是 `kind=access` 上的一个角色串……所以本仓**不因它升 kit 版本**，pin 的 `v0.1.1` 已能验」**只有一半成立**，另一实测证伪：

- ✅ 成立的一半：`httpadapter.Authorize` 的角色 any-of 是**精确串匹配**，不吃 kit 的角色枚举 ⇒ 策略表加 `service` 无需新机制。
- ❌ 错的一半：`v0.1.1` 的 `authenticate()` 在进策略表**之前**无条件要求 `claims.UserIDInt64()`，而裁-17 的 token 口径是 `sub=service:<repo>`（非数字）⇒ 真·服务 token 恒 401 `malformed token subject`。
  `TestServedPolicyServiceRole` 当时能绿，是因为它用 `IssueTokens` 签**数字 subject** + `role=service`，恰好绕开了这个形状——测试证明的是策略表对，不是链路通。

**处置**：本仓 pin 升 `v0.1.4`（kit 只对 `claims.Role == auth.ServiceRole` 放宽该校验，其余输入仍 401；`v0.1.4/go.mod` hash 与 `v0.1.1` 逐字节相同 ⇒ 依赖图未变）。
决策 1/3/4、启动闸口径、`JWT_SECRET` 配发仍在 core QT-71 那条腿——这些都没被这条追加改动。
**验收**：`go build/vet/test ./...` 的退出码取自 CI（本机无 Go 工具链，不拿本机绿当结论）。

## 追加（2026-11-12）· 决策 4 的「无 secret + 回环 = 开放」作废，改为三态

2026-11-12 安全审计确认 `internal/httpapi/auth.go` 的 `if a.svc == nil || !a.svc.Enabled() { return "", nil }` 等价于「鉴权没启用 = 已通过」；`cmd/dataservice/main.go` 把 `DecideStartup` 的 `allowInsecure` 硬编码成 true；`deploy/compose.yaml` 还内置公开签名密钥 `dev-only-change-me`。三条叠加后，任何不配 `JWT_SECRET` 的部署都会把 `POST /ingest/raw`、`POST /ingest/points`、`POST /sync/jobs`、`POST /sync/schedules`、`POST /api/v1/ohlcv/bulk` 等写面直接暴露。

**新口径（六仓统一）**：

1. 有 `JWT_SECRET` ⇒ 全闸：写面必须带 token + 角色。
2. 无 secret + **回环绑定** + 未显式声明 ⇒ 进程可起，读面公开，**写面一律 503 `auth_unavailable`**；无 secret + **非回环绑定** + 未声明 ⇒ **拒绝启动**（错误点名缺 secret 且绑定地址不是回环）。
3. 无 secret + 逐字 `AUTH_INSECURE_EXPOSURE=loopback-published` ⇒ 任意绑定全放行，启动必须 WARN 同时点名「当前写面无鉴权」与**实际**绑定地址（非回环时追加「已对外暴露」），声明值单独标注；未知声明值 ⇒ 拒绝启动。

**处置**：`NewAuthorizer` 在无 secret 时按 `IsMutating` 拒绝写面（`ErrAuthUnavailable`）；显式开放改由 `NewOpenAuthorizer` 承担；启动判定收敛到 `decideAuthPosture`，第 2 态补上绑定地址检查（`isLoopbackAddr`），与其余五仓同口径；compose 的 `JWT_SECRET` 默认值删除，缺省从环境 / `.env` 注入。

决策 1/2/3 不受影响；本条只覆盖决策 4 的启动闸口径。
