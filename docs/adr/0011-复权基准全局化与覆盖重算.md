# ADR-0011 · 复权基准全局化与覆盖重算

- 状态：已采纳（2026-11-12）
- 决策：本仓（数据面负责人）
- 关联：ADR-0004（写面幂等用内容比对）、ADR-0007（传输与调度自持）、`docs/dataflow.md` §2「复权基准与重算」、`docs/api-schema.md` §1、`docs/db-schema.md` §1.1 / §9.1

## 背景

日线取数的 qfq 口径原来是：`前复权价 = 当日价格 × 当日复权因子 / **请求区间内最新**复权因子`。于是复权基准取决于「当初用哪个窗口拉的」：

- `600036.SH` 补 2025 数据后基准变成 2025-12-31（因子 6.3201），而 `600000.SH` / `600519.SH` 是按 2024 年窗口的基准算的；
- 同一 `(symbol, trade_date)` 因此有两个 `close`，回测结果取决于数据是分几次、按什么窗口拉进来的，不可复现；
- 扩窗补历史会让既有价格整体变动，但写面是 `ON CONFLICT DO NOTHING` + 内容比对（ADR-0004），异内容触发 `ErrContentConflict` **整批回滚**——想对齐旧口径，一行业都写不进去，必须先手工删行。

这与「数据面唯一写者、可审计」的原则冲突：历史数据只能增不能改，且「怎么算的」没有记账。

## 决策

1. **基准全局化**。基准因子取 `market.adjust_baseline_changes` 中该 symbol 的最新记录，**不随请求区间变化**。解析顺序固定：
   1. 账本有记录 ⇒ 用它；
   2. 无账本但 `market.ohlcv_daily_qfq` 已有该 symbol 行 ⇒ 用 `MAX(trade_date)` 及其当日因子，追加 `reason=bootstrap`；
   3. 首次入库 ⇒ 用本次窗口的最新因子，追加 `reason=bootstrap`。
2. **账本 append-only**：`market.adjust_baseline_changes(id, symbol, base_date, base_factor, previous_date, previous_factor, reason, changed_at)`。`reason ∈ {bootstrap, manual}`，`base_factor > 0` 有 CHECK；`bootstrap` 每 symbol 一条（局部唯一索引），并发首拉只有赢家写入，输的一方**读回赢家的基准**再算价格。不提供 UPDATE / DELETE 口径。
3. **基准不自动推进**：新数据到达不会移动已有基准，否则每个增量作业都要重写全部历史。基准的推进是一次显式的、可审计的运维动作。
4. **覆盖重算路径**：`POST /api/sync/jobs` 的 `extra` 支持
   - `overwrite`（布尔，缺省 `false`）：`true` 时写面改用 `ON CONFLICT (pk) DO UPDATE`，幂等（重跑行数不变、内容稳定）；
   - `baseline_date`（`YYYY-MM-DD` / `YYYYMMDD`）：人工改基准，**必须**同时给 `overwrite=true`，且只允许 `job_type=ohlcv_daily`；缺一即入队期 400 `invalid_parameter`。
   改基准会追加一条 `previous_date/previous_factor` 齐全的 `reason=manual` 记录；同一基准重放不追加（幂等）。基准日当天必须查得到 `adj_factor`，否则拒绝（没有因子的日期不能当基准）。
5. **不静默回退**：传输的基准账本未装配时，日线取数直接失败。不保留「没有账本就按窗口算」的兼容分支——那正是本 ADR 要消灭的口径。
6. **不自动改写既有数据**：本 ADR 只提供能力与账本。`600000.SH` / `600519.SH` 等既有行的基准对齐需要一次显式的 `baseline_date + overwrite` 作业，由数据面负责人按窗口批准后执行，不在建表/部署时顺手重写。

## 代价与已知限制

- **基准与「今天」的距离会随时间变大**：pin 在 bootstrap 日的 qfq 序列，越晚的日期越偏离「以最新日为基准」的直觉。这是可复现性的代价；需要重定时走决策 4，而不是每夜自动推进。
- **旧数据的基准是重建的**：对 ADR 生效前已入库的 symbol，用 `MAX(trade_date)` 重建。正常情况（作业写入了窗口内全部有因子的交易日）它等于老口径的基准；尾部停牌等边缘情形可能有偏差，需用 `overwrite` 作业校正。
- **改基准与写入不是同一事务**：账本在取数阶段写入，数据在 ETL 阶段落库。若写入阶段失败，账本已指向新基准；重跑同一 `baseline_date + overwrite` 作业会收敛（幂等）。非 overwrite 的后续作业会因内容冲突响亮失败，不会被静默写入。
- **并发人工改基准**：两个 manual 变更并发时后写者赢；这是运维动作，要求串行执行，未加锁。
- **账本 `changed_at` 是唯一时序**：没有 job_id 关联；定位是哪次作业触发的变更，需按时间对照 `ingest.sync_jobs`。

## 验证

- `internal/transport/tushare/baseline_test.go`：
  - `TestFetchDailyOHLCV_BaselineIsPinnedAcrossWindows`：同一区间在不同窗口拉两次，重叠日期的 `close` 完全相同；账本只有一条 bootstrap。
  - `TestFetchDailyOHLCV_BootstrapFromPersistedData`：无账本 + 已有数据 ⇒ 用 `MAX(trade_date)` 重建基准，窗口外因子单查一次。
  - `TestFetchDailyOHLCV_ManualBaselineChangeIsAuditableAndIdempotent`：改基准后价格按新因子变化，manual 记录带 `previous_*`，同基准重放不追加。
  - `TestFetchDailyOHLCV_RequiresBaselineLedger` / `TestFetchDailyOHLCV_ManualBaselineWithoutFactorIsInvalidInput`。
- `internal/store/adjust_baseline_pg_test.go`（`DATABASE_URL` 门控）：append-only、bootstrap 唯一、`previous_*`、`LatestTradeDate`。
- `internal/store/write_pg_test.go`：`TestPG_BulkInsertWithOptions_OverwriteRewritesAndIsIdempotent`（覆盖写不改行数、重跑哈希不变）；既有 `TestPG_BulkInsert_ConflictingContentRollsBackWholeBatch` 保持（非 overwrite 仍整批回滚）。
- `internal/sync`：`baseline_date` 缺 `overwrite` / 非日线 / 非字符串 / 非日期 / `overwrite` 非布尔一律 `ErrInvalidParams`。
- 破坏验证（2026-11-12）：把基准解析退回「区间最新因子」⇒ 一致性用例红；把覆盖分支退回 `DO NOTHING` ⇒ 重算用例红（`ErrContentConflict`）。逐字节还原后复绿。
